# Rental Manager

A simple Rental Management System: rooms → tenants → electricity meter readings → monthly bills → PDF → WhatsApp → payments.

Built with Vue 3 + TypeScript + Vite + Tailwind CSS + Supabase, deployable as a free static site on GitHub Pages and as an Android app via Capacitor.

---

## 1. Supabase setup

1. Create a free project at [supabase.com](https://supabase.com).
2. Open **SQL Editor** → paste the contents of [`supabase/schema.sql`](./supabase/schema.sql) → **Run**.
   This creates all tables (`properties`, `rooms`, `tenants`, `meter_readings`, `bills`, `payments`), constraints, and Row Level Security policies.
   - **Already deployed the old single-property version and have real data?** Don't re-run `schema.sql`. Instead run [`supabase/migrate_to_multi_property.sql`](./supabase/migrate_to_multi_property.sql) once — it creates the `properties` table, migrates your old settings row into your first property, and attaches all existing rooms to it automatically.
3. (Optional, for tenant ID document uploads) In **Storage**, create a **private** bucket named `tenant-documents`. Uncomment and run the storage policy block at the bottom of `schema.sql`.
4. Go to **Authentication → Providers** and make sure **Email** is enabled.
5. Go to **Authentication → Users → Add user** and create your admin account (email + password). This is the only login V1 supports.
6. Go to **Project Settings → API** and copy:
   - **Project URL** → `VITE_SUPABASE_URL`
   - **anon public key** → `VITE_SUPABASE_ANON_KEY`

   Never use the `service_role` key in the frontend.

## 2. Running locally

```bash
npm install
cp .env.example .env
# edit .env and paste your Supabase URL + anon key
npm run dev
```

Open the printed local URL and log in with the admin account you created in Supabase.

To type-check and build for production:

```bash
npm run build   # runs vue-tsc, then vite build → outputs to dist/
npm run preview # serve the production build locally
```

## 3. Deploying to GitHub Pages

1. Push this repo to GitHub.
2. In **Settings → Pages**, set **Source** to **GitHub Actions**.
3. In **Settings → Secrets and variables → Actions**, add two repository secrets:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
4. Push to `main` (or run the workflow manually from the **Actions** tab). `.github/workflows/deploy.yml` builds the app with your secrets and publishes `dist/` to Pages.
5. Your app will be live at `https://<your-username>.github.io/<repo-name>/`.

Routing uses hash history (`/#/rooms`, `/#/bills`, etc.) specifically so it works correctly on GitHub Pages without any server-side rewrite rules.

## 4. Android setup & testing (Capacitor)

Prerequisites: [Android Studio](https://developer.android.com/studio) installed, with an emulator or a physical device connected (USB debugging enabled).

```bash
npm run build
npx cap sync android
npx cap open android
```

This opens the project in Android Studio. From there:
- Click **Run ▶** to install and launch on a connected device/emulator.
- The app loads the bundled web build (`dist/`) — no server required — and talks directly to Supabase over the internet, so the device needs network access.

Whenever you change the web app, re-run `npm run build && npx cap sync android` before testing again (or use the shortcut `npm run android:sync`).

### Generating a debug APK

Either:
- In Android Studio: **Build → Build App Bundle(s) / APK(s) → Build APK(s)**. The APK appears under `android/app/build/outputs/apk/debug/app-debug.apk`.

Or from the command line:
```bash
cd android
./gradlew assembleDebug
```
The APK is written to `android/app/build/outputs/apk/debug/app-debug.apk` — install it on any Android device (`adb install app-debug.apk`) or share it directly.

Publishing to the Google Play Store is not required/covered for Version 1.

## 6. Managing multiple locations

- Go to **Properties** first and add each location (name, owner, address, contact numbers, UPI ID, bill prefix, due day). Every property has its own contact info and bill numbering.
- Then go to **Rooms** and assign each room to a property. Room numbers only need to be unique *within* a property — e.g. `101` can exist at both "Main Street" and "Downtown".
- Dashboard, Bills, Meter Readings, and Reports all have a property filter dropdown once you have more than one property — pick a specific location or leave it on "All Properties" for a combined view.
- Generated bills and PDFs automatically use the correct property's name, address, bill prefix, and due day based on which property the room belongs to.

## 7. How billing works (important business rules)

- Every room has its own rent, electricity rate, water charge, and maintenance charge.
- A tenant's **agreed rent** defaults to their room's rent but can be overridden per tenant. Changing the room's default rent later does not change an existing tenant's agreed rent.
- A bill starts as a **draft**: rent/electricity/water/maintenance/other charge/discount are pulled from current room + tenant + meter reading data, but are editable.
- **Finalizing** a bill locks in the exact amounts used at that time — permanently. If the room's rent or electricity rate changes next month, this bill is never recalculated.
- Previous due carries forward from the prior bill's outstanding balance, so dues are never double-counted.
- A `unique(room_id, tenant_id, billing_month)` database constraint prevents duplicate bills.

## 8. Security notes

- Row Level Security is enabled on every table; only authenticated users can read/write.
- The frontend only ever uses the Supabase **anon** key (safe to expose) — RLS is what actually protects the data.
- `.env` is git-ignored; only `.env.example` (with placeholder values) is committed.
